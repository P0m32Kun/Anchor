# Anchor 护网实战定位与运行模式梳理

> 背景：用户提出当前最大的问题不是继续堆功能，而是先明确“Anchor 这工具到底应该如何运行，应该具备哪些功能，如何为护网行动提供帮助”。
> 核心诉求：**个人开发者工具，足够收敛** — 输入目标，输出结果；自动化调用工具、筛选干扰、快速定位脆弱资产。
> 本文档基于现有代码、架构文档、设计文档做诚实差距分析，不美化现状。

---

## 一、当前 Anchor 是什么

### 1.1 产品定位（README 原话）

> 面向授权安全测试的目标中心工作台，通过编排成熟开源工具、强制范围校验、统一结果模型、人工验证队列和报告生成，减少安全人员在工具切换、数据整理、证据归档和报告交付上的重复劳动。

### 1.2 当前已实现的核心能力

| 能力域 | 实现状态 | 说明 |
|--------|---------|------|
| 资产驱动扫描引擎 | ✅ 已上线 | `internal/scanengine/`，非固定流水线，资产→Work→工具→新资产的循环 |
| Scope Check | ✅ 已上线 | 域名/URL/IP/CIDR 匹配，exclude-only 默认策略 |
| 多目标类型 | ✅ 已上线 | domain / ip / cidr / url / company（FOFA/Hunter/Quake 展开） |
| 工具编排 | ✅ 已上线 | Subfinder→dnsx→cdncheck→naabu→nmap→httpx→Katana→ffuf→Spoor→Nuclei |
| 指纹驱动 Nuclei | ✅ 已上线 | httpx technologies → Nuclei `-tags`，无指纹自动跳过 |
| 多 Worker 调度 | ✅ 已上线 | 最少负载优先 + round-robin + 故障转移 |
| 被动搜索 | ✅ 已上线 | FOFA/Hunter/Quake 并行，fail-soft |
| Finding 管理 | ✅ 已上线 | confidence/priority 评分、批量写入缓冲、人工验证队列 |
| 报告导出 | ✅ 已上线 | Markdown / JSON，8 章节模板 |
| Docker 部署 | ✅ 已上线 | Server/Worker/Frontend 三镜像，install.sh 向导 |
| 代码测试 | ✅ 已修复 | 37 package 全绿，覆盖率 86%；E2E 74 tests 可加载 |

### 1.3 当前执行模型

**不是流水线，是资产驱动循环**：

```
目标输入 → Scope Check → 种子资产注入
  ↓
发现资产 → DeriveEligibleWorks(资产类型) → 派生 Work(资产×动作)
  ↓
执行工具 → 输出解析 → 发现新资产 → 循环
  ↓
idle_timeout → wind_down → stopped
```

扫描模式：外网（low-noise，速率保守）/ 内网（all-in，全工具全端口）

## 二、个人开发者护网场景的核心诉求

### 2.1 我们的用户是谁

- **个人开发者 / 小团队**：1-3 人，非企业级安全部门
- **护网/渗透测试场景**：有明确时间窗口，需要在窗口内最大化攻击面覆盖
- **核心诉求**：输入目标，输出结果。不花时间在工具切换、数据整理上

### 2.2 核心价值主张

> **输入目标，输出结果** — 自动化调用各工具、筛选干扰信息、快速定位脆弱资产

三个关键词：
1. **自动化** — 一键启动，自动编排所有工具，不用手动一个个跑
2. **筛选** — 海量扫描结果中自动过滤误报、低危信息，只保留真正有价值的
3. **收敛** — 最终输出是可操作的脆弱资产清单 + 证据，不是原始数据 dump

### 2.3 护网场景下的真实需求

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 快速启动扫描 | P0 | 输入域名/IP，一键启动，少配置 |
| 自动资产发现 | P0 | 自动枚举子域、端口、服务、Web 资产 |
| 智能漏洞初筛 | P0 | 指纹驱动 Nuclei，只跑相关模板，减少噪音 |
| 干扰信息过滤 | P0 | 自动过滤 CDN/WAF、内网地址、重复资产 |
| 脆弱资产优先级 | P0 | 按 severity/confidence/影响范围排序，critical 在前 |
| 证据链完整 | P0 | 每个脆弱资产附带 HTTP request/response + 复现步骤 |
| 扫描进度可见 | P1 | 知道当前在扫什么、发现了多少、预计剩余时间 |
| 报告导出 | P1 | 一键导出 Markdown/PDF，直接用于报告 |
| 误报标记 | P1 | 快速标记 false_positive，减少下次噪音 |
| 多目标批量 | P1 | 护网通常有多个目标，支持批量导入+批量扫描 |

### 2.4 不需要什么（收敛原则）

| 功能 | 为什么不需要 | 建议 |
|------|-------------|------|
| 多项目管理/战情室 | 个人开发者一次盯一个项目，不需要全局 Dashboard | 维持单项目视角 |
| 用户系统/RBAC | 个人/小团队不需要分权 | 不做 |
| 复杂调度系统 | 护网时间窗口管理不是核心痛点 | 维持手动启动 |
| 持续监控 | 护网是一次性行动，不是赏金猎人 | 不做 |
| SIEM/Webhook 集成 | 个人开发者不需要对接企业安全平台 | 不做 |
| Tauri 桌面端 | 已删除，Web 界面足够 | 维持 Web |
| 供应链/SBOM | 护网核心是攻击面发现，不是资产清单管理 | P2 再议 |

| 脆弱资产优先级 | ⚠️ 部分 | 🟠 | 有 confidence/priority 评分，但 UI 展示不够突出 |
| 证据链完整 | ⚠️ 部分 | 🟠 | 有 raw request/response，但缺截图 + 复现步骤 |

### 3.2 真实差距（Top 3）

| 差距 | 影响 | 当前状态 | 建议 |
|------|------|---------|------|
| **干扰信息过多** | 护网扫描产生海量 Finding，真实风险被淹没 | 有基础评分，但无智能降噪 | 新增基于历史的误报模式学习 |

| **启动门槛高** | 护网时间紧，配置越少越好 | 已有 Docker 部署，但首次启动仍需较多步骤 | 优化 install.sh，减少手动配置 |

## 四、建议的改进方向（收敛版）

### P0 — 核心体验（护网必需）

| # | 改进 | 为什么重要 | 落点 |
|---|------|-----------|------|
| 1 | **智能干扰过滤** | 护网扫描噪音大，需要自动降噪 | 新增 `internal/scoring/noise_filter.go`，基于历史误报模式自动降级 |
| 2 | **证据链增强** | 脆弱资产需要截图才能快速确认 | 集成 eyewitness/nuclei screenshot 到 Finding |
| 3 | **一键启动优化** | 护网时间紧，减少配置步骤 | 优化 install.sh + 默认配置 |

### P1 — 体验提升

| # | 改进 | 为什么重要 | 落点 |
|---|------|-----------|------|
| 4 | **Finding 优先级重排序** | 护网需要快速定位 critical，不要翻几十页 | 前端 FindingPage 默认按 severity × confidence 排序 |
| 5 | **批量误报标记** | 海量 Finding 需要批量操作 | 前端支持多选 + 批量标记 false_positive |
| 6 | **扫描时间预估** | 护网有时间窗口，需要预估剩余时间 | 基于已完成的 Work 数量和速率，预估剩余时间 |

### P2 — 锦上添花

| # | 改进 | 为什么重要 |
|---|------|-----------|

## 五、当前不应做的事

1. **不要加战情室/多项目管理** — 个人开发者不需要，维持单项目视角
2. **不要加用户系统/RBAC** — 个人/小团队不需要
3. **不要做持续监控** — 护网是一次性行动
4. **不要加 Tauri 桌面端** — 已删除，Web 足够
5. **不要盲目加新工具** — 当前 10 个工具已覆盖护网主路径
6. **不要改资产驱动模型** — 方向正确，收敛而非扩展

## 六、结论

Anchor 的**底层引擎（资产驱动 + Scope Check + 工具编排）** 已经具备护网基础能力。当前最大瓶颈不是缺功能，而是**信息过载** — 海量扫描结果淹没了真正的脆弱资产。

建议下一步优先做 P0 的三项改进，核心方向是：
- **更智能的筛选**（自动降噪）
- **更完整的证据**（截图 + 复现步骤）
- **更快的启动**（减少配置）

把 Anchor 从「功能齐全的扫描引擎」收敛为「**输入目标、输出脆弱资产的个人护网利器**」。
